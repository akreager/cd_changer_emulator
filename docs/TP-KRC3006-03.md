## 1. Purpose and Scope

This document defines the test procedures for developing, validating, and integrating a Raspberry Pi-based CD changer emulator to replace a Kenwood compact disc auto-changer on a compatible head unit’s 13-pin mini-DIN CD-CH port.

This test plan begins where TP-KRC3006-01 ends. TP-KRC3006-01 covers passive protocol capture and command mapping using a KDC-C717 changer. This document covers active emulation: making an ATtiny1616 replicate the CD changer’s protocol behavior, integrating the Raspberry Pi for audio playback, and validating the complete system.

The procedures are structured in four sequential phases. Each phase has defined entry criteria, step-by-step procedures, expected results, and pass/fail criteria. All test results shall be recorded in the companion Test Log workbook (TL-KRC3006-03.fods).

## 4. Test Phases

Testing is divided into four sequential phases. Each phase has entry criteria that must be satisfied before beginning. Do not skip phases; later phases depend on validated results from earlier ones.

### 4.1 Phase 1: ATtiny1616 Handshake Emulation

**Objective:** Program the ATtiny1616 to respond to the head unit’s idle polling messages (captured in TP-KRC3006-01 Phase 2A) with a valid handshake. The head unit should recognize a changer is connected and transition out of its “no changer” display state. This is the critical proof-of-concept milestone.

**Entry Criteria:**

> • TP-KRC3006-01 complete. Idle polling message structure decoded and documented in TL-KRC3006-01.

> • MCU-01, PRG-01, MOD-04, MOD-03 available and functional.

> • ATtiny1616 verified working: upload a test blink sketch via UPDI Friend using megaTinyCore in the Arduino IDE.

> • Head unit bench power setup validated (from TP-KRC3006-01 Phase 1).

**Reference:** Record all results on Test Log Tab “Phase 1 — Handshake.”

#### 4.1.1 Level Shifter Setup

1. The ATtiny1616 breakout runs at 3.3 V. The Kenwood bus operates at 5 V. A bidirectional level shifter is required for all signal connections between them.

2. For breadboard prototyping, use BSS138-based 4-channel bidirectional level shifter modules (two modules provide 8 channels). For the final HAT, the design targets the SN74LVC8T245PWR (two chips, one per direction — see DN-KRC3006-01).

3. Connect the level shifter low-voltage reference (LV) to 3.3 V from the ATtiny1616 breakout’s 3.3 V output pin. Connect the high-voltage reference (HV) to 5 V. For the 5 V source during breadboard prototyping, use one of the following:

   **a.** A 5 V bench supply (preferred — independent, clean).

   **b.** A 7805 or LM1117-5.0 regulator fed from the head unit’s Pin 3 (B.U. 12 V). This is raw, unfiltered battery voltage — add a 100 µF electrolytic and 100 nF ceramic on the input and output.

   **c.** A USB power source. Do NOT use the ATtiny breakout’s USB 5 V — it backfeeds through the 3.3 V regulator.

   Record the 5 V source used on the test log.

4. Verify both voltage rails with the multimeter before connecting any signals. Record measured LV and HV voltages.

#### 4.1.2 ATtiny1616 Wiring

1. Connect the ATtiny1616 to the breakout board (MOD-03) via the level shifter. Route all signals through the level shifter — no direct connections between the ATtiny and the Kenwood bus. Use the following pin assignments (from DN-KRC3006-01):

   | ATtiny Pin | CD-CH Pin | Signal | Direction | Notes |
   |----|----|----|----|----|
   | PA3 (SPI SCK) | Pin 13 | CLK | Input | Hardware SPI clock |
   | PA4 (SPI MOSI) | Pin 11 | CH-DATAH | Input | Data from head unit |
   | PA5 (SPI MISO) | Pin 10 | CH-DATAC | Output | Data to head unit |
   | PA6 | Pin 1 | CH-REQH | Input | Pin-change interrupt, falling edge |
   | PA7 | Pin 9 | CH-REQC | Output | Changer handshake |
   | PB0 | Pin 4 | CH-CON | Input | Changer connect/enable |
   | PB1 | Pin 5 | CH-MUTE | Output | Mute control, initialize HIGH |
   | PB2 | Pin 7 | CH-RST | Input | Reset from head unit |
   | GND | Pin 2 | GND | — | Common ground through level shifter |

   > **NOTE:** Do not connect PA1 (UART TX) or PA2 (UART RX) yet — those are for the Pi serial link in Phase 3.

2. Connect the logic analyzer (LA-01) to the breakout board’s test headers in parallel with the ATtiny connections. Use the channel map in TP-KRC3006-01 §4.2.1 (Phases 2A/2B; CH6 is RESET, not the Phase 2C CLK-H tap). This allows simultaneous observation of head unit transmissions and ATtiny responses.

3. Double-check all connections against the wiring table. Verify with the multimeter that no signal line is shorted to 5 V, 3.3 V, 12 V, or GND. Verify that GND is common between the ATtiny breakout, level shifter, head unit (Pin 2), and logic analyzer.

> **CAUTION:** During development, power the ATtiny breakout from USB (laptop) and the head unit from the bench PSU. All signal connections between them must pass through the level shifter. Do NOT connect the ATtiny to the head unit’s +12 V (Pin 3).

#### 4.1.3 Handshake Implementation

1. Using the idle polling message structure captured in TP-KRC3006-01 Phase 2A, write ATtiny1616 firmware (megaTinyCore, Arduino IDE) that:

   **a.** Monitors CH-CON (PB0) — only respond when the head unit has selected CD changer mode.

   **b.** Monitors CH-REQH (PA6) for a falling edge via pin-change interrupt.

   **c.** When CH-REQH goes LOW, reads data bytes on CH-DATAH (PA4/MOSI) clocked by CLK (PA3/SCK) using the hardware SPI peripheral in slave mode.

   **d.** After receiving the complete polling message, pulls CH-REQC (PA7) LOW to acknowledge.

   **e.** Loads a response into the SPI data register for transmission on CH-DATAC (PA5/MISO), synchronized to CLK.

   **f.** Releases CH-REQC HIGH after transmission completes.

2. For the initial response, use the minimum viable status message: “changer present, no disc loaded.” Refer to the Mictronics documentation and the captured C717 responses from TP-KRC3006-01 Phase 2B. Using a “no disc” response is safer than claiming discs are loaded before audio is working.

3. Confirm CH-CON polarity before coding the enable check. TP-KRC3006-01 Phase 1 measured the actual voltage on Pin 4 in both states. If active-LOW (per service manual analysis), the ATtiny should check PB0 == LOW as the precondition for responding. If active-HIGH (per some published docs), check PB0 == HIGH. Use the measured result, not assumptions.

4. Hold CH-MUTE (PB1) LOW during initialization. Release it HIGH only after the first successful handshake exchange completes. This prevents audio pops during startup.

5. Monitor CH-RST (PB2). If RESET is asserted by the head unit, reinitialize the protocol state machine and restart the handshake sequence.

6. Upload the firmware via the UPDI Friend (PRG-01). Start a logic analyzer capture, then power on the head unit and select CD changer source.

7. Examine the logic analyzer capture. Compare the ATtiny’s response against the C717’s response captured in TP-KRC3006-01 Phase 2B. Record the following on the test log:

   **a.** Does the ATtiny respond within the timing window established by the C717 captures?

   **b.** Are the response bytes correct (compare hex values byte-by-byte)?

   **c.** Is the CH-REQC handshake timing (assert LOW, release HIGH) consistent with the C717 behavior?

8. The critical success indicator is the head unit’s display. It should change from the “NO CHANGER” / searching state to something acknowledging a connected changer (e.g., “NO DISC” or equivalent). Photograph the display and record the exact text on the test log.

9. If the handshake fails, use the logic analyzer capture to diagnose the failure mode. Common issues include:

   **a.** Response too slow (ATtiny misses the timing window — check interrupt latency).

   **b.** SPI clock polarity or phase mismatch (data sampled on wrong edge — try CPOL/CPHA combinations).

   **c.** Bit order wrong (MSB vs LSB first — compare against captured C717 data).

   **d.** Wrong byte count in response (compare frame length against C717 capture).

   **e.** CH-REQC timing wrong (asserted too early, too late, or for wrong duration).

   **f.** Level shifter introducing excessive propagation delay (measure with scope if available).

   Record each attempt and its outcome on the test log. Iterate until handshake succeeds.

**Pass Criteria:** Head unit display changes from “no changer” state to “changer connected” state (e.g., “NO DISC”). Logic analyzer capture shows valid bidirectional data exchange matching the timing profile of the real C717. No error states triggered on the head unit.

> **NOTE:** Expected iterations: This phase typically requires 5–15 firmware iterations to get the handshake timing right. The test log has space for multiple attempts.

### 4.2 Phase 2: Command Response Implementation

**Objective:** Implement ATtiny1616 firmware responses for every head unit command documented in the TP-KRC3006-01 command map. The head unit should display disc/track information and accept all transport controls without dropping the changer connection.

**Entry Criteria:** Phase 1 passed — handshake stable. Head unit recognizes the ATtiny as a connected changer. Complete command map available from TP-KRC3006-01.

**Reference:** Record results on Test Log Tab “Phase 2 — Commands.”

#### 4.2.1 Status Response Implementation

1. Update the ATtiny firmware to respond to status polls with “disc loaded, stopped” status. Report disc 1 present with a plausible track count (e.g., 10 tracks). Use the status byte format captured from the real C717 in TP-KRC3006-01. This should cause the head unit to enable its transport controls (play, next, prev, etc.).

2. Verify the head unit display shows disc and track information. Record the exact display text and photograph it.

3. If the head unit drops the connection or shows an error state after initially recognizing the changer, the status response format is likely wrong. Compare the ATtiny’s response byte-by-byte against the C717 capture. Pay attention to:

   **a.** Status flags (playing vs stopped, disc loaded vs empty, error bits).

   **b.** Disc number encoding (BCD vs binary, 0-indexed vs 1-indexed).

   **c.** Track number encoding.

   **d.** Any checksum or parity byte at the end of the status message.

#### 4.2.2 Transport Command Responses

1. Working through the command map from TP-KRC3006-01, implement firmware responses for each command in the following priority order:

   **a.** Play — Respond with “playing” status, disc 1, track 1. If TP-01 Phase 2B found a time field, also return that field incrementing about once per second (R-5).

   **b.** Stop / Pause — Respond with “stopped” status, retain current disc/track.

   **c.** Next Track — Increment track number in status response.

   **d.** Previous Track — Decrement track number in status response.

   **e.** Disc Change (up/down or direct select) — Update disc number in status response. Assert MUTE LOW for 200–500 ms during the transition, then release HIGH.

   **f.** Repeat mode toggle — Set/clear repeat flag in status response.

   **g.** Shuffle/Random mode toggle — Set/clear shuffle flag in status response.

2. For each command, the test procedure is:

   **a.** Start a logic analyzer capture.

   **b.** Press the button on the head unit.

   **c.** Verify the ATtiny receives the expected command bytes (compare against TP-KRC3006-01 command map).

   **d.** Verify the ATtiny sends the correct updated status response.

   **e.** Verify the head unit display updates accordingly.

   **f.** Stop capture, save as P2_cmd\_\[name\]\_\[sequence\].sr.

   **g.** Record the result (pass/fail, display text, any anomalies) on the test log.

3. Test command sequences that the head unit may issue automatically:

   **a.** End of disc — What happens when the ATtiny reports the last track has ended? Does the head unit send a “next disc” command, or does it expect the changer to auto-advance?

   **b.** Disc change completion — After a disc change command, how long does the head unit wait for the new disc’s status before timing out?

   **c.** Error recovery — If the ATtiny deliberately sends a malformed response, does the head unit retry, reset, or drop the connection? Document the retry/timeout behavior.

4. If TP-01 Phase 2B identified a time field, increment it at approximately 1 s/s and verify by capture that it matches the C717's behavior. Otherwise skip and record N/A. The KRC-3006 display does not show elapsed time; display criteria follow the instruction manual's “Clock display” and “CD auto changer mode” sections ([R-5](../.agents/rulings/2026-10-16.md)).

#### 4.2.3 Connection Stability Test

With all commands implemented, let the ATtiny respond to head unit polling continuously for 30 minutes. Toggle through several commands (play, next track, disc change, stop, play again) during this period. Monitor for:

1. Protocol disconnections (head unit reverts to “no changer” state).

2. Display freezes or corrupted information.

3. Missed polls (visible as gaps in the logic analyzer capture).

4. Gradual timing drift.

   Record the duration and any incidents on the test log.

**Pass Criteria:** All commands from the TP-KRC3006-01 command map produce correct status responses and head unit display updates. 30-minute stability test completes with no protocol disconnections. MUTE line asserts correctly during disc changes.

### 4.3 Phase 3: Audio Playback Integration

**Objective:** Connect the Raspberry Pi with I2S DAC to the audio input pins, establish a serial command bridge between the ATtiny and the Pi, and achieve end-to-end music playback controlled by the head unit’s buttons.

**Entry Criteria:** Phase 2 passed — all commands implemented and stable. Raspberry Pi configured with OS and audio software. GY-PCM5102A DAC module tested independently (plays audio to headphones or powered speaker).

**Reference:** Record results on Test Log Tab “Phase 3 — Integration.”

#### 4.3.1 DAC Audio Chain Setup

1. Connect the GY-PCM5102A DAC module to the Raspberry Pi’s GPIO header:

   | Pi GPIO | Pi Header Pin | DAC Signal            |
   |---------|---------------|-----------------------|
   | GPIO18  | Pin 12        | BCK (bit clock)       |
   | GPIO19  | Pin 35        | LRCK (L/R word clock) |
   | GPIO21  | Pin 40        | DIN (serial data)     |

   Tie the DAC module’s SCK pin to GND (the PCM5102A generates its own system clock internally).

2. Connect the DAC to the CD-CH port via the pass-through breakout board and a 3.5 mm male-to-male audio cable.

3. If TP-KRC3006-01 Phase 1 determined that Pin 6 (D.GND) and Pin 2 (GND) are isolated inside the head unit, keep the DAC ground connected ONLY to Pin 6 and run a separate digital ground to Pin 2. If they are tied together internally, a single ground connection to either pin is acceptable.

4. Configure the Pi audio output for the I2S DAC. Add to /boot/config.txt:

   dtoverlay=hifiberry-dac

   Reboot and verify with “aplay -l” that the DAC appears as a sound device.

5. Test audio independently before connecting to the head unit. Play a known audio file through the DAC into headphones or a powered speaker. Verify clean output with no audible hiss, hum, or distortion. Record the result.

#### 4.3.2 ATtiny–Pi Serial Bridge

1. Connect the ATtiny’s UART to the Raspberry Pi’s GPIO UART:

   | ATtiny Pin | Pi GPIO      | Pi Header Pin | Signal                       |
   |------------|--------------|---------------|------------------------------|
   | PA1 (TX)   | GPIO15 (RXD) | Pin 10        | ATtiny transmit → Pi receive |
   | PA2 (RX)   | GPIO14 (TXD) | Pin 8         | Pi transmit → ATtiny receive |

   > **NOTE:** Both the ATtiny (3.3 V) and the Pi GPIO (3.3 V) operate at the same voltage level. No level shifting is needed on the UART lines.

2. Define a serial command protocol between the ATtiny and Pi. Use a simple newline-terminated ASCII format for readability during debugging:

   ATtiny → Pi (head unit button presses):

   PLAY\n

   STOP\n

   NEXT\n

   PREV\n

   DISC:N\n (where N = 1–10)

   REPEAT:ON\n REPEAT:OFF\n

   SHUFFLE:ON\n SHUFFLE:OFF\n

   FF:START\n FF:STOP\n

   REW:START\n REW:STOP\n

   Pi → ATtiny (playback state for status responses):

   STATE:PLAY:D:TT:MM:SS\n (D=disc, TT=track, MM:SS=elapsed)

   STATE:STOP:D:TT\n

   STATE:LOAD:D\n (disc change in progress)

   STATE:ERROR:CODE\n

   Baud rate: not specified (D-12). Select it in §4.3.2a.


##### 4.3.2a UART rate selection

Approved [R-6](../.agents/rulings/2026-10-16.md) implements D-12. Record results in TL-03 “Phase 3 — Integration”, UART Rate Selection. Until a checksum is designed and approved in DN-01, count malformed lines as parse errors.

1. Test candidate rates **9600, 38400 and 115200** on the actual wiring.
2. For each rate:
   - **Bit-time error:** transmit `0x55` continuously from the ATtiny. Measure the analyzer frequency (baud/2 nominal) and record error in percent.
   - **Soak:** exchange **10,000 STATE/command message pairs**; count framing and parse errors.
   - **Latency:** over **20 presses**, measure from the head-unit /REQ H edge to the Pi playback command being logged; record maximum latency and the timing method.
   - If possible, repeat bit-time error measurements cold (**<10 °C**) and warm (**>40 °C**); record temperatures or “not tested”.
3. Select the **lowest** rate with zero soak errors, bit-time error below the architect's margin, and maximum latency below the owner's limit. The margin is set after measurement; both limits remain pending and must be recorded before selection. Record the selected rate and rationale in TL-03, then update DN-01/DN-05 (DC-21).

##### 4.3.2 continued — Serial bridge implementation

3. Update the ATtiny firmware to:

   **a.** Translate received Kenwood bus commands into serial messages to the Pi.

   **b.** Parse STATE messages from the Pi and update the protocol status response accordingly.

   **c.** Continue handling all Kenwood bus communication in real time — the UART communication must not block or delay SPI interrupt handling.

4. Implement a Python service on the Pi that:

   **a.** Listens on the serial port for command messages from the ATtiny.

   **b.** Controls audio playback via python-mpv in response to commands.

   **c.** Sends STATE updates back to the ATtiny at regular intervals (~1 per second during playback) with current disc, track, and elapsed time.

   **d.** Maps disc numbers (1–10) to folders: CD01/ through CD10/, each containing numbered FLAC audio files (01.flac, 02.flac, etc.).

5. Test the serial bridge independently before connecting audio. Send simulated commands from the Pi’s serial console and verify the ATtiny responds correctly on the Kenwood bus. Then send simulated commands from the ATtiny (or a test sketch) and verify the Pi starts/stops playback. Record results.

#### 4.3.3 End-to-End Validation

1. Organize test audio files on the Pi’s storage: CD01/ through CD10/, each containing numbered FLAC files. Use at least 3 discs with at least 5 tracks each for meaningful testing.

2. Power on the full system: bench PSU for head unit, USB power for ATtiny breakout and Pi. Verify the head unit recognizes the changer and displays disc/track information.

3. Test each command from the Phase 2 command map and verify correct end-to-end behavior:

   | Command | Expected Behavior |
   |----|----|
   | Play | Audio begins from speakers. Head unit displays T-01 and the disc number (R-5). |
   | Stop / Pause | Audio stops. Display shows stopped state, retains disc/track. |
   | Next Track | Audio advances to next file. Display updates track number. |
   | Previous Track | Audio returns to previous file. Display updates. |
   | Disc Change | Audio mutes briefly (200–500 ms). Pi switches to new folder. Audio resumes. Display shows new disc number. |
   | Repeat | Current track loops continuously. |
   | Shuffle | Tracks play in random order within current disc/folder. |
   | Fast Forward (hold) | Audio scrubs forward (if implemented) or skips to next track. |
   | Fast Reverse (hold) | Audio scrubs backward or skips to previous track. |

   Record pass/fail for each command on the test log. Save a logic analyzer capture for any command that fails.

4. Test boundary conditions:

   **a.** Last track of a disc — Does the system advance to the next disc, stop, or repeat?

   **b.** First track, previous — Does the system wrap to the last disc, stay on track 1, or restart?

   **c.** Disc with no files — Does the system report “no disc” gracefully?

   **d.** Very short tracks (\<5 seconds) — Does rapid track advancement cause protocol issues?

   **e.** Very long tracks (\>10 minutes) — Playback continues past 10 min; track and disc display stay correct; if a time field exists, verify by capture that it does not wrap or corrupt (R-5).

5. Audio quality assessment. With audio playing through the head unit’s speakers:

   **a.** Listen for hum at 60 Hz or 120 Hz (ground loop). If present, check ground isolation between Pin 2 and Pin 6.

   **b.** Listen for hiss (DAC noise floor). Should be inaudible at normal listening levels.

   **c.** Listen for digital artifacts (clicks, pops, dropouts). May indicate I2S timing issues or buffer underruns.

   **d.** Adjust the DAC output level via ALSA mixer if audio is too hot (distorted) or too quiet.

   Record the audio quality assessment on the test log.

**Pass Criteria:** All mapped commands produce correct audio and display behavior. Audio quality is clean with no audible hum, hiss, or digital artifacts at normal listening volume. Serial bridge operates without blocking protocol communication.

### 4.4 Phase 4: Soak Testing and Power Cycle Validation

**Objective:** Validate system reliability under sustained operation, power cycling, and simulated fault conditions. This phase demonstrates the system is ready for vehicle installation or HAT PCB design.

**Entry Criteria:** Phase 3 passed — all commands working, audio clean, no protocol drops during Phase 3 testing.

**Reference:** Record results on Test Log Tab “Phase 4 — Soak Test.”

#### 4.4.1 Sustained Playback Test

1. Configure the Pi to play a playlist spanning multiple discs (at least 3 disc folders, 30+ tracks total). Begin playback and let the system run continuously for a minimum of 2 hours. During the test:

   **a.** Periodically toggle commands (next track, disc change, pause/play) — at least once every 15 minutes.

   **b.** Monitor the head unit display for correct disc/track updates.

   **c.** Listen for audio quality degradation over time.

   **d.** Record the start time, end time, any incidents, and the total track count played on the test log.

2. Monitor for the following failure modes:

   **a.** Protocol disconnection (head unit reverts to “no changer” — most critical).

   **b.** Audio dropout or stuttering (buffer underrun, I2S timing drift).

   **c.** Display freeze (ATtiny stops updating status).

   **d.** Serial bridge stall (Pi stops sending STATE updates, or ATtiny stops forwarding commands).

   **e.** Memory leak on ATtiny or Pi (check ATtiny free SRAM periodically via debug output; check Pi memory usage with “free -m”).

#### 4.4.2 Power Cycle Recovery

1. With the system in “playing” state, turn off both staged power adapter switches (simulating ignition off). Wait 5 seconds. Turn both switches back on.

2. Record the recovery behavior:

   **a.** How quickly does the head unit resume polling for a changer?

   **b.** Does the ATtiny reinitialize and respond to the first poll?

   **c.** Does the head unit display return to a “changer connected” state?

   **d.** Time from power-on to functional changer display: \_\_\_\_\_\_ seconds.

   **e.** Does the Pi need to reboot, or does it survive on its own power source?

3. Repeat the power cycle test 5 times. Record each recovery time. All 5 should recover successfully.

4. Test a rapid power cycle: off for 1 second, then on. This simulates a brief ignition interruption. Verify the system recovers without requiring a full reboot.

#### 4.4.3 Reset Line Test

1. While the system is operating normally, observe the behavior of CH-RST (Pin 7) during a power cycle. Record with the logic analyzer:

   **a.** Does the head unit send a reset pulse on power-up?

   **b.** What is the pulse width and polarity?

   **c.** How long after power-on does the first reset pulse appear?

   **d.** How long after reset does the first polling message appear?

#### 4.4.4 Mute Line Verification

1. During a disc change command, verify with an oscilloscope or logic analyzer that:

   **a.** CH-MUTE (Pin 5) goes LOW before the audio transition.

   **b.** CH-MUTE returns HIGH after the new track begins.

   **c.** The mute duration is appropriate (200–500 ms — long enough to suppress pops, short enough to not be annoying).

   **d.** Audio output is actually silent during the mute period (listen and verify).

#### 4.4.5 Head Unit Power-Off Behavior

1. With the system in “playing” state, switch the head unit source away from CD changer (to radio or tape). Record:

   **a.** Does CH-CON (Pin 4) change state immediately?

   **b.** Does the head unit stop polling?

   **c.** Does the ATtiny detect the source change and enter an idle state?

   **d.** Switch back to CD changer — does the system resume without a full reinitialization?

2. Turn the head unit fully off (power button, not PSU off). Record whether Pin 3 (B.U.) remains at 12 V (expected — it is battery-unswitched). Record whether the ATtiny detects the loss of polling activity.

**Pass Criteria:** 2-hour soak test completes with no protocol disconnections or audio dropouts. Power cycle recovery succeeds within 5 seconds on all 5 attempts. Rapid power cycle (1-second off) recovers without a full reboot. MUTE line operates correctly during disc changes. Source switching (away from CD changer and back) works without reinitialization.

## 5. Incident Reporting

When a test produces unexpected results, record a Test Incident on the “Incidents” tab of the test log workbook. Each incident should include: the phase and step where it occurred, what was expected versus what was observed, a photograph or logic analyzer screenshot if applicable, and the root cause once determined.

Severity classification:

> • Critical: Head unit damaged, magic smoke, or safety concern. STOP all testing immediately.

> • Major: Protocol communication fails entirely; cannot proceed to next phase.

> • Minor: Specific command doesn’t work as expected, but overall protocol functions.

> • Observation: Behavior differs from documentation but does not affect functionality.

For an open-source project, incidents are valuable documentation. Even resolved issues should be preserved in the project repository as they help future builders troubleshoot similar problems.

## 6. File Naming Convention

> • Logic analyzer captures: P\[phase\]\_\[description\]\_\[sequence\].sr (e.g., P1_handshake_attempt_003.sr)

> • Screenshots/photos: P\[phase\]\_\[description\]\_\[sequence\].png

> • Firmware versions: fw_v\[major\].\[minor\]\_\[description\].ino (e.g., fw_v0.1_handshake_only.ino)

> • Test logs: TL-KRC3006-03.fods

Commit all artifacts to the project Git repository at the end of each test session.

## 7. Safety Precautions

> • Always verify polarity before applying power to the head unit.

> • Keep the bench PSU current limit at 2 A (raise to 3 A only if needed for startup inrush, then reduce).

> • Never connect the ATtiny1616 directly to the 5 V Kenwood bus. All signals must pass through the level shifter.

> • Do not connect the ATtiny breakout or Raspberry Pi to Pin 3 (+12 V) during breadboard prototyping. Use separate USB power for both.

> • If any component becomes hot to the touch or produces smoke or unusual odor, immediately disconnect all power and investigate before proceeding.

> • When eventually installing in a vehicle, disconnect the vehicle battery negative terminal before working on any wiring.

> • Lead-free solder is recommended. Work in a ventilated area when soldering.
