## 1. Purpose and Scope

This document defines the test procedures for reverse engineering the serial communication protocol between a Kenwood KRC-3006 aftermarket car stereo head unit and its companion CD changer, connected via a 13-pin mini-DIN connector. The objective is to fully characterize the protocol—message structure, timing, command set, and handshake behavior—to enable future development of a hardware emulator.

The procedures are structured in sequential test phases, each building on the results of the previous phase. Each phase has defined entry criteria, step-by-step procedures, expected results, and pass/fail criteria. All test results shall be recorded in the companion Test Log workbook (TL-KRC3006-01.ods).

This document covers only protocol capture and analysis. Emulation development and integration testing are covered separately in TP-KRC3006-03.

This document is modeled on the IEEE 829-2008 standard for test documentation, adapted for hardware protocol reverse engineering. It is intended for publication as part of an open-source project and should be treated as a living document updated throughout the project.

## 4. Test Phases

Testing is divided into sequential phases. Each phase has entry criteria that must be satisfied before beginning. Do not skip phases; later phases depend on validated results from earlier ones.

### 4.1 Phase 1: Bench Setup and Static Verification

**Objective:** Establish a powered bench test setup and verify the 13-pin DIN connector pinout against the factory service manual schematic. Confirm power, ground, and signal voltage levels with no changer connected.

**Entry Criteria:** Head unit (KEN-01), bench PSU (PWR-01), staged power adapter (PWR-02), KRC-3006 DC cord (PWR-03), multimeter (DMM-01), 13-pin mini-DIN cable (CBL-01), 13-pin mini-DIN breakout (MOD-02), and service manual available.

**Reference:** Record all measurements on Test Log Tab “Phase 1 — Static Verification.”

#### 4.1.1 Power Harness Preparation

1. Identify the head unit power connector using the service manual wiring diagram. Locate the +12 V constant (B+), +12 V accessory/ignition (ACC), ground (GND), and illumination wires.

2. Set the bench PSU to 12.0 V with a current limit of 2.0 A. Do not turn on yet.

3. Connect the bench power supply output to the staged power adapter input. Ensure both toggle switches (constant power and ignition power) are in the OFF position.

4. Connect the staged power adapter output harness to the head unit DC cord.

> **CAUTION:** The KRC-3006 may draw a brief inrush current on power-up. If the PSU trips, increase the current limit to 3 A momentarily, then reduce after startup. Typical running current is 0.5–1.5 A.

#### 4.1.2 Initial Power-Up

1. Turn on the bench PSU.

2. Turn on the constant-power toggle on the staged power adapter. This provides battery-unswitched power (B+) to the head unit for memory retention.

3. Turn on the ignition-power toggle on the staged power adapter. Verify the head unit powers on and displays normally.

4. Record the steady-state current draw on the test log (expected: 0.5–1.5 A at idle with no audio playing).

5. Set the head unit source to CD CHANGER (may require pressing SRC or a dedicated CD-CH button). The display should show an error or searching message (e.g., “NO MAGAZINE” or “NO DISC”). Record the exact display text.

#### 4.1.3 13-Pin DIN Static Voltage Measurements

1. With the head unit powered on and set to CD changer source, use the multimeter to measure DC voltage on each of the 13 pins relative to pin 2 (digital ground). Record every measurement on the test log form.

2. Cross-reference each measured voltage against the expected values in the following pinout table. Flag any discrepancies for investigation.

**Expected 13-Pin DIN Pinout** (based on published documentation and service manual cross-reference):

| Pin | Signal Name | Function | Direction | Notes |
|----|----|----|----|----|
| 1 | CH-REQH | Request (H→C) | Output | Head unit pulls LOW to initiate transfer |
| 2 | GND | Digital Ground | — | Primary ground reference for all signals |
| 3 | +12V | Power Supply | Output | Battery voltage to power changer (≈300 mA typical) |
| 4 | CH-CON | Changer Connect | Output | Active-LOW when head unit activates CD changer mode (verify Phase 1) |
| 5 | CH-MUTE | Mute Request | Input | Changer pulls LOW to mute audio during disc changes |
| 6 | AGND | Audio Ground | — | Separate ground for audio signals; verify continuity to pin 2 |
| 7 | CH-RST | Reset | Output | Reset pulse from head unit on power-up or error recovery |
| 8 | R-CH | Right Audio | Input | Right channel analog audio from changer (≈1–2 V RMS) |
| 9 | CH-REQC | Request (C→H) | Input | Changer pulls LOW to initiate or acknowledge transfer |
| 10 | CH-DATAC | Data (C→H) | Input | Changer-to-head-unit serial data, valid on falling CLK edge |
| 11 | CH-DATAH | Data (H→C) | Output | Head-unit-to-changer serial data, valid on rising CLK edge |
| 12 | L-CH | Left Audio | Input | Left channel analog audio from changer (≈1–2 V RMS) |
| 13 | CLK | Clock | Output | 125 kHz synchronous clock generated by head unit |

3. Verify pin 3 shows +12 V (±0.5 V). This confirms the head unit supplies power through the changer port.

4. Verify pin 4 (CH-CON) state when CD changer source is selected and when switched to another source (radio, tape). Toggle the source and record both states. Note: CH-CON is expected to be active-LOW per service manual analysis; confirm polarity.

5. Measure pin 13 (CLK). If the head unit is actively polling for a changer, you may see a DC average voltage between 0 and 5 V (the clock is toggling). A true 0 V or 5 V means the clock is static. Record the observed value.

6. Verify pin 6 (audio ground) has continuity to pin 2 (digital ground) OR is isolated. Record which. If isolated, this confirms separate audio and digital ground planes, which affects the emulator grounding strategy.

**Pass Criteria:** Pin 2 is ground. Pin 3 reads 11.5–12.5 V. Pin 4 toggles with source selection. All pins measured and recorded. No unexpected short circuits detected.

**Incident Handling:** If pin 3 shows 0 V, check whether the head unit requires ACC/ignition to enable changer power. If any signal pin shows a voltage outside the 0–5.5 V range, STOP and investigate using the service manual schematic before connecting the logic analyzer.

### 4.2 Phase 2A: Idle Protocol Capture — Head Unit Only

**Objective:** Capture the head unit’s polling/initialization messages sent when no changer is connected. These unanswered transmissions reveal the message structure, timing, and initialization sequence without needing to generate any responses.

**Entry Criteria:** Phase 1 passed. Logic analyzer (LA-01) available. PulseView software installed and verified working with the analyzer.

**Reference:** Record results on Test Log Tab “Phase 2 — Idle Capture.”

#### 4.2.1 Logic Analyzer Setup

1. Install PulseView on your computer. Connect the logic analyzer via USB and verify it is recognized (Devices menu should show “fx2lafw” or similar).

2. Connect the logic analyzer channels to the 13-pin DIN connector as follows. Use the jumper wires included with the analyzer. Connect the analyzer’s GND to pin 2 of the DIN connector breakout.

| LA Channel | DIN Pin | Signal Name | Purpose                          |
|------------|---------|-------------|----------------------------------|
| CH0 (D0)   | Pin 13  | CLK         | Synchronous clock from head unit |
| CH1 (D1)   | Pin 11  | CH-DATAH    | Data: head unit → changer        |
| CH2 (D2)   | Pin 10  | CH-DATAC    | Data: changer → head unit        |
| CH3 (D3)   | Pin 1   | CH-REQH     | Request handshake from head unit |
| CH4 (D4)   | Pin 9   | CH-REQC     | Request handshake from changer   |
| CH5 (D5)   | Pin 4   | CH-CON      | Changer connect/enable           |
| CH6 (D6)   | Pin 7   | CH-RST      | Reset signal                     |
| GND        | Pin 2   | GND         | Ground reference                 |

> **NOTE:** Per SparkFun’s documentation, the GND pin adjacent to CH6 on some analyzer units may not be true ground. Use the GND pin at the opposite end of the header, or verify with your multimeter first.

3. In PulseView, set the sample rate to 1 MHz (8× oversampling of the 125 kHz clock gives clean capture without excessive file sizes). Set the sample count to 2M samples (2 seconds of capture).

#### 4.2.2 Idle Capture Procedure

1. Power on the head unit. Select CD changer as the source.

2. Wait 10 seconds for the head unit to enter its polling loop. Some head units send initialization sequences immediately; others wait before beginning periodic polls.

3. In PulseView, click “Run” to begin capture. Let it capture the full 2-second window.

4. Examine the capture. Look for the following characteristics and record them on the test log:

> • Is the clock (CH0) running continuously, or does it burst during transmissions only?

> • What is the measured clock frequency? (Use PulseView’s frequency measurement on the CLK channel.)

> • How frequently do transmission bursts occur? (Measure the interval between consecutive polling attempts.)

> • What is the state of CH-REQH (CH3) during transmissions? (Expected: pulls LOW before data, returns HIGH after.)

> • Is any data visible on CH-DATAH (CH1)? (Expected: yes — the head unit sends polling bytes.)

> • Is CH-DATAC (CH2) completely flat? (Expected: yes — no changer is connected to respond.)

5. Save the capture file in PulseView’s native .sr format AND export a screenshot/PNG of a single complete polling message. Name the files with the pattern: P2A_idle_capture_001.sr and P2A_idle_capture_001.png.

6. Repeat the capture at least 3 times to verify the polling pattern is consistent. Record any variations.

#### 4.2.3 Idle Message Decoding

1. Zoom into a single polling message in PulseView. Identify the start and end of the data frame by observing when CH-REQH goes LOW and returns HIGH.

2. Count the number of clock cycles during the transmission. This tells you the total bits transmitted.

3. Try PulseView’s SPI protocol decoder: set CH0 as CLK, CH1 as MOSI (head unit data), and CH2 as MISO (changer data). Set clock polarity and phase to capture data on the rising edge, MSB first.

4. Record the decoded bytes in hexadecimal. Compare these bytes against the Mictronics protocol documentation. The first bytes should match a known address/header pattern.

5. If the SPI decoder doesn’t produce clean results (possible due to the custom handshake), manually decode: mark each rising clock edge on CH0, read the corresponding bit value from CH1, and group into bytes (MSB first, 8 bits per byte).

6. Document the complete idle polling message structure: header bytes, command byte, data bytes (if any), and total message length. Record this on the test log.

**Pass Criteria:** At least one complete idle polling message decoded to hex bytes. Clock frequency measured. Polling interval measured. Message structure identified and compared against published protocol documentation. All captures saved.

### 4.3 Phase 2B: Protocol Capture — With CD Changer

**Objective:** Capture bidirectional protocol traffic between the head unit and a known-working KDC-C717 CD changer connected through the breakout pass-through board (MOD-03). Observe the full initialization handshake, status polling, and changer responses.

**Entry Criteria:** Phase 2A passed. KDC-C717 changer (KEN-02) available and loaded with a known-good disc magazine. Breakout pass-through board (MOD-03) assembled, verified, and tested per TP-KRC3006-02. Logic analyzer connected per Phase 2A channel assignments.

**Reference:** Record results on Test Log Tab “Phase 2B — Changer Capture.”

#### 4.3.1 Physical Setup

1. With all power removed (both staged power adapter switches OFF), connect the breakout pass-through board (MOD-03) inline between the head unit’s 13-pin DIN port and the KDC-C717 changer cable.

2. Connect the logic analyzer probes to the breakout board’s test points using the same channel assignments as Phase 2A.

3. Load the KDC-C717 magazine with at least one known-good audio CD in slot 1. Note the total number of discs loaded and the track count of disc 1.

4. Verify all connections are secure. Confirm no signal wires are shorted to ground or power using the multimeter in continuity mode.

#### 4.3.2 Initialization Capture

1. Power on the bench PSU. Turn on both staged power adapter switches (constant power, then ignition power).

2. Immediately start a PulseView capture (2M samples at 1 MHz) to catch the initialization sequence.

3. Select CD changer source on the head unit. Observe whether the KDC-C717 powers up, loads a disc, and begins playback.

4. Record the initialization sequence. Note:

> • The handshake sequence: which side transmits first, and how many exchanges occur before the changer reports status.

> • The timing between the head unit’s first poll and the changer’s first response.

> • Whether CH-CON (pin 4) changes state during initialization.

> • Whether CH-MUTE (pin 5) is asserted by the changer during disc loading.

5. Allow playback to stabilize for 30 seconds, then capture again to observe steady-state periodic status messages.

6. Compare the changer’s responses against the idle polls captured in Phase 2A. Identify which bytes in the response correspond to disc number, track number, and playback state.

7. Save all capture files as P2B_init_NNN.sr and P2B_steady_NNN.sr.

**Pass Criteria:** Complete initialization handshake captured and decoded. Changer response message structure identified. Steady-state status message format documented. All captures saved with screenshots of key exchanges.

### 4.4 Phase 3: Command Mapping

**Objective:** Systematically map every head unit command (play, pause, next track, next disc, etc.) by pressing each button while capturing the full bidirectional protocol exchange with the KDC-C717 connected. Build a complete command reference table.

**Entry Criteria:** Phase 2B passed. Head unit and KDC-C717 are communicating and playback is functional through the breakout board.

**Reference:** Record results on Test Log Tab “Phase 3 — Command Map.”

#### 4.4.1 Systematic Button Capture

1. Ensure the KDC-C717 is in a known state: disc 1 playing, mid-track (not at the beginning or end of a disc).

2. Prepare a systematic button matrix. For each button/action on the head unit face, you will perform one capture. The buttons to test include:

> • Play / Pause

> • Next Track / Previous Track

> • Fast Forward (hold Next Track)

> • Fast Reverse (hold Previous Track)

> • Disc Up / Disc Down (or direct disc select buttons 1–6/10)

> • Repeat mode toggle

> • Random/Shuffle mode toggle

> • Any other buttons that are active in CD changer mode

3. For each button:

> • (a) Start a logic analyzer capture.

> • (b) Press the button once.

> • (c) Stop capture.

> • (d) Decode the command bytes sent by the head unit.

> • (e) Decode the response bytes sent by the changer.

> • (f) Record both the command and response hex values on the test log form.

> • (g) Save the capture file as P3_cmd\_\[name\]\_NNN.sr.

4. For commands that produce a state change (e.g., next track should cause the changer to seek and update its status), capture the full exchange including the changer’s updated status response. Note any multi-message sequences.

5. Test edge cases: press next track on the last track of a disc, previous track on track 1, disc up on the last loaded disc, and disc select for an empty slot. Record how the changer responds in each case.

#### 4.4.2 Command Map Compilation

1. Build the definitive command map table from your captures. For each command, record: the hex byte(s) sent by the head unit, the expected changer response, and any observed timing constraints.

2. Compare every byte against the Mictronics documentation. Note any commands that differ from the published protocol.

3. Identify any undocumented commands or status codes observed during testing.

**Pass Criteria:** All accessible head unit controls mapped to hex command bytes. At least play, stop, next/previous track, and disc selection confirmed. Changer responses for each command documented. Command map table complete and cross-referenced against published documentation.

## 5. Incident Reporting

When a test produces unexpected results, record a Test Incident on the “Incidents” tab of the test log workbook. Each incident should include: the phase and step where it occurred, what was expected versus what was observed, a photograph or logic analyzer screenshot if applicable, and the root cause once determined.

For an open-source project, incidents are valuable documentation. Even resolved issues should be preserved in the project repository as they help future builders troubleshoot similar problems.

Severity classification:

> • Critical: Head unit damaged, magic smoke, or safety concern. STOP all testing immediately.

> • Major: Protocol communication fails entirely; cannot proceed to next phase.

> • Minor: Specific command doesn’t work as expected, but overall protocol functions. Can proceed.

> • Observation: Behavior differs from documentation but does not affect functionality.

Commit all artifacts to the project Git repository at the end of each test session.

## 7. Safety Precautions

> • Always verify polarity before applying power to the head unit.

> • Keep the bench PSU current limit at 2 A (raise to 3 A only if needed for startup, then reduce).

> • Never connect the logic analyzer to the 13-pin DIN connector while the head unit is unpowered and the PSU is off. Static discharge could damage components.

> • If any component becomes hot to the touch or produces smoke or unusual odor, immediately disconnect power and investigate before proceeding.

> • When eventually installing in a vehicle, disconnect the vehicle battery negative terminal before working on any wiring.

> • Lead-free solder is recommended. Work in a ventilated area when soldering.
